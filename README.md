# ipi-io-probe

在优化轨迹输出之前，先把它的真实代价量出来。

`probe.py` 不改 i-PI，纯外部计时，模拟 i-PI 的写行为——**每个 bead 一个文件、
每次输出每个文件一次写、句柄常驻**——然后用同样多的数据量跑一遍合并写，
让你在自己的文件系统上看到差多少。

## 用法

在**计算节点**上，指向**你实际会写的那个文件系统**：

```bash
python probe.py --path /scratch/$USER/iotest \
                --natoms 192 --beads 32 --frames 2000 \
                --step-ms 10          # 可选：你实测的每步耗时，用来算占比
```

`--step-ms` 填上之后，脚本会直接告诉你 I/O 占 wall time 的百分比，
以及一句判断：低于 5% 就别折腾缓冲了，去调 `stride` 更划算。

## 四个模式，为什么要都跑

| 模式 | 说明 |
|---|---|
| `per-frame` | 逐帧写，不 fsync —— **i-PI 的默认行为** |
| `per-frame+sync` | 逐帧写 + fsync —— i-PI 设 `<flush>1</flush>` 时的行为 |
| `buffered` | 攒到 `--chunk-mb` 再写，不 fsync |
| `buffered+sync` | 攒到 `--chunk-mb` 写并 fsync |

**这一步是整件事的关键。** 不 fsync 的写往往只是把数据拷进 page cache 就返回了，
你量到的是 memcpy 的速度，不是磁盘的速度。`per-frame` 和 `per-frame+sync`
之间能差两个数量级，这个差距才是真正会拖慢作业的部分。
只看 `per-frame` 那一行就下结论，是最常见的自欺。

## 怎么读结果

```
mode              total (s)     MB/s  writes   p50/ev   p99/ev   max/ev
per-frame             0.018    996.7      60    0.172    0.960    1.140
per-frame+sync        0.626     28.3      60    9.968   20.133   24.044
buffered              0.016   1120.5      16    0.115    0.485    0.485
buffered+sync         0.281     63.1      16    4.725    6.596    6.596
```

- **total** — 整段写完的墙钟时间，这是唯一能直接换算成"作业多跑了多久"的量
- **writes** — 实际发生了几次写调用。缓冲的收益全在这个数字上
- **p50/p99/max `/ev`** — 已经归一化到「每次输出事件」，所以不同模式之间可以比。
  **看 p99 不要看 p50**：共享文件系统上的问题基本都是长尾，平均值得不到信息
- 上面是本地 SSD 的结果（所以 `per-frame` 能跑到 1 GB/s，完全看不出问题）。
  换到 Lustre 上，`per-frame` 那行通常会难看得多

## 五个坑

1. **在登录节点跑没有意义。** 登录节点和计算节点的 I/O 路径、并发度都不一样。
2. **不 fsync 的基准不可信。** 见上。
3. **Lustre 上先看 stripe。** `lfs getstripe 你的目录` —— stripe count 为 1 时，
   所有写都打到一个 OST 上，再大的缓冲也救不了。
4. **单进程测不到竞争。** 真实的"有时候很慢"多半是别人在抢 OST。
   同一个脚本在一天的不同时段跑几次，比较 p99 的漂移，比单次结果有信息量。
5. **缓冲是要付代价的**：进程被杀（walltime、OOM、节点故障）时，
   内存里没落盘的部分直接消失。HPC 上这不是小概率事件。
   真要做，就得挂 SIGTERM handler 在退出前强制 flush。

## 如果量出来确实值得

再考虑写一个缓冲后端（`TrajectoryOutput` 的子类，攒够再落盘 + 信号处理）。
在那之前，有几个更便宜的办法值得先试：

- 把 `<trajectory>` 的 `stride` 调大——改一个数字，收益通常最大
- 换二进制格式（XTC / HDF5）——体积小一个数量级，写次数不变但每次写的字节更多
- 写到节点本地 NVMe，作业结束再 stage 到共享盘
